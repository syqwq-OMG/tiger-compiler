Tiger Interpreter   

Since you have not finished the register allocation part yet, your assembly can't link using GCC. We use Tiger Interpreter to help you judge if your answer is right. This interpreter takes the assembly file (`.s`) as input and interprets your assembly code even without register allocation. Your final assembly code should act as follows:   
```
movq t112, %rsp   
addq %rcx, %rbx   
leaq L1(t118), %rdi   
```
This code doesn't make any sense, but it shows what assembly code you should generate in this lab, where `t1xx` represents a temporary register not allocated yet. Note that you can use machine registers now, and you must use them for some special instructions (like `imul`/`idiv`, ret value). We only support the following instructions now: `movq`, `addq`, `subq`, `imulq`, `idivq`, `leaq`, `callq`, `cmpq`, `jmp`, `je`, `jne`, `jg`, `jge`, `jl`, `jle`, `retq`, `cqto`, which is enough for you to finish this lab.   

Besides, we have provided a debugger inside this interpreter to help you figure out what is going wrong; details can be found in the following Appendix A. Tiger Interpreter's source code is in `scripts/lab5_test`, and is written in python.   

Implementation Tips   

1. As discussed in class, when performing canonicalization, expressions that contain side effects—such as `CALL (f())`—must be evaluated before the surrounding expression that uses them. This means extracting the side-effecting expression, assigning its result to a temporary variable, and replacing the original sub-expression with that temporary in the pure expression. This transformation ensures that all expressions become side-effect-free, which simplifies code generation and allows for more effective optimizations. For implementation details, refer to the files under `src/tiger/canon/`.   
2. Figure out what information a frame typically stores. Additionally, you must distinguish between caller-saved and callee-saved registers:   
   - Caller-saved registers must be saved by the calling function if it wants to preserve their values across a function call.   
   - Callee-saved registers must be saved and restored by the callee function if it uses them.   
3. In the x86-64 System V ABI: The first six function arguments are passed via registers and the remaining arguments go on the stack. Access the rest of them using offsets from a saved frame pointer.   
4. Don't forget to generate proper prologue and epilogue code for each function:   
   - In the prologue, allocate space on the stack (based on total frame size) and save callee-saved registers if they are used.   
   - In the epilogue, restore callee-saved registers and deallocate the stack frame before returning.   
   - Also make sure to correctly maintain the return address and return value in `%rax`.

Tiger Interpreter Supported Commands   

- **ni:** Execute the next instruction   
- **continue:** Continue execution until the program crashes or hits a breakpoint (similar to `c` in gdb, but also includes the function of `r`)   
- **b:** Set a breakpoint in two ways:   
  - By line number: Note that the line number corresponds to the compiler's line numbers, which can be viewed using the interpreter. For example, `b 40` sets a breakpoint at line 40.   
  - By function name: This is simpler, but note that external call functions do not follow this process. For example, `b bsearch` sets a breakpoint at the bsearch function.   
- **disable:** Similar to gdb, but without an enable option, making it more like delete. Note that the input is the breakpoint number, which can be viewed with `show b`.   
- **disassemble:** Similar to gdb, displays the current executing assembly instructions and surrounding instructions. Note that only the line numbers here are accurate.   
- **show:** This command includes functionalities of gdb's `p`, `x`, and `show`:   
  - `show registers`: Displays all register values, including mechanical and temporary registers.   
  - `show machine`: Displays all mechanical register values.   
  - `show temp`: Displays all temporary register values.   
  - `show memory`: Outputs current memory address values in order.   
  - `show memtable`: Outputs current memory address values in a table format.   
  - `show b`: Displays information on all breakpoints.   
- **exit:** Exit debug mode.   

The functionality is quite limited. If you find any bugs in our source code or have better suggestions, feel free to contact the TA.   

Tips   

- The Tiger Interpreter's debug mode will halt and perform a disassemble upon encountering any error. You can now use `show` to inspect the problematic registers or memory addresses and check all instructions that modified the relevant addresses or registers, setting breakpoints as needed to identify the issue.   
- GDB is a powerful tool, and the following commands are highly recommended:   
  - `p`: Very useful for printing function outputs and the values of various object members, as well as performing type casts.   
  - `x`: Mainly used to inspect memory addresses.   
  - `watch`: Monitors changes to memory addresses.   
- Those interested might want to explore record & replay, a GDB feature with reverse execution capabilities. It is very useful but has a high learning curve, so choose based on your needs.   
- The key to debugging is not the tool but the approach. For a highly modular project like Tiger-Compiler, it is crucial to first locate the error. Especially when there are no exceptions but the results are incorrect, you must learn to pinpoint the error step by step. If necessary, you can read the trace output to determine whether the issue lies in Translation or Codegen.
